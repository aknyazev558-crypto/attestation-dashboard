# Аттестация директоров ДЦ

Next.js (App Router) + Supabase (Auth + Postgres + Row Level Security).

## 1. Настройка Supabase

Проект уже подключён (см. `.env.local`, не коммитится в git):

```
NEXT_PUBLIC_SUPABASE_URL=...
NEXT_PUBLIC_SUPABASE_ANON_KEY=...
SUPABASE_SERVICE_ROLE_KEY=...
```

Если разворачиваете с нуля — создайте проект на [supabase.com](https://supabase.com) и возьмите
из Settings → API: Project URL, anon/publishable key и **service_role (secret) key**.

`SUPABASE_SERVICE_ROLE_KEY` — серверный секрет, полностью обходит RLS. Используется только в
Server Actions (`app/dashboard/actions.ts`, функция `assignDirector`) для приглашения новых
директоров через Supabase Auth Admin API. **Никогда** не добавляйте к нему префикс
`NEXT_PUBLIC_` и не коммитьте в git — иначе он попадёт в браузерный бандл и любой сможет
обойти защиту базы данных.

### Redirect URL для писем-приглашений

По умолчанию Supabase отправляет ссылки в письмах на **Site URL** проекта (обычно
`http://localhost:3000` — сработает только если приглашённый откроет письмо на компьютере, где
в этот момент запущен `npm run dev`, что нереалистично для реальных директоров). Приложение
само просит Supabase перенаправлять на `/auth/set-password` (страница, где директор задаёт
пароль), но этот адрес нужно один раз внести в список разрешённых:

Authentication → URL Configuration:
- **Site URL** — задайте адрес деплоя (после Vercel — `https://<ваш-проект>.vercel.app`; для
  локальной разработки можно оставить `http://localhost:3000`).
- **Redirect URLs** — добавьте `http://localhost:3000/auth/set-password` (для локальных тестов)
  и `https://<ваш-проект>.vercel.app/auth/set-password` (после деплоя). Без этого Supabase
  проигнорирует адрес из приглашения и всё равно отправит на голый Site URL.

Если приглашение уже отправлено до этой настройки — просто назначьте директора ещё раз через
ту же кнопку в `/dashboard` (для уже созданного пользователя это переотправит приглашение).

### Применить схему и RLS

Файлы миграций лежат в `supabase/migrations/`:

- `0001_schema.sql` — таблицы `branches`, `profiles`, `cycles`, `attestations`, `ipr_items`
- `0002_rls.sql` — функция `is_owner()` и политики Row Level Security
- `0003_ceo_role.sql` — роль `ceo` (те же права, что у `owner` — `is_owner()` расширена на неё),
  поле `attestations.ceo_comment` и `ipr_items.source` (`'owner' | 'ceo'`)
- `0004_self_assessment_submit.sql` — `attestations.self_submitted` и три поля
  `achievement_1/2/3` вместо одного `achievements`
- `0005_login_events.sql` — таблица `login_events` (журнал входов) с RLS: писать
  можно только своё событие, читать — только владельцу/CEO
- `0006_staff_block_access.sql` — роль `staff`, `profiles.position` (произвольная
  должность) и таблица `staff_block_access` (доступ к конкретным блокам оценки)
- `0007_competency_blocks.sql` — таблица `departments` (7 блоков: Продажи, ППО, HR,
  Маркетинг, КЦ, CQ, FinDep) и таблица `competencies` (компетенции переехали из
  `lib/competencies.ts` в базу); `staff_block_access.block_id` с этой миграции
  указывает на `departments`, а не на старые весовые блоки 1–4
- `0008_competency_departments_many.sql` — компетенция теперь может относиться сразу
  к нескольким блокам компетенций: связь `competencies` ↔ `departments` вынесена в
  таблицу `competency_departments` (many-to-many), колонка `competencies.department_id`
  удалена
- `0009_editable_weights.sql` — таблица `scoring_blocks` (4 весовых блока итоговой
  оценки, вес и название теперь редактируются владельцем/CEO — раньше были зашиты в
  `lib/competencies.ts`) и `competencies.weight` (вес компетенции внутри её весового
  блока, по умолчанию 1)
- `0010_staff_scores.sql` — `attestations.staff_scores`: отдельная колонка для оценки
  сотрудника, раньше сотрудники писали прямо в `manager_scores`

**Вариант А — Supabase CLI:**

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push
```

**Вариант Б — вручную:** откройте в Supabase проекте SQL Editor и по очереди выполните
содержимое `supabase/migrations/0001_schema.sql`, `0002_rls.sql`, `0003_ceo_role.sql`,
`0004_self_assessment_submit.sql`, `0005_login_events.sql`, `0006_staff_block_access.sql`,
`0007_competency_blocks.sql`, `0008_competency_departments_many.sql`,
`0009_editable_weights.sql`, затем `0010_staff_scores.sql`.

### Создать пользователей (Фаза 3)

**Владельца** заводим один раз вручную (курицу и яйцо не обойти — назначать роли пока некому):

1. Authentication → Users → **Add user** (email + пароль, без письма — быстрее для первого
   входа) или **Invite user** (письмо со ссылкой на установку пароля).
2. Table Editor → `profiles` → добавить строку: `id` — скопировать id только что созданного
   пользователя, `role = 'owner'`.

**Директоров** дальше можно назначать прямо в приложении — на странице `/dashboard` в колонке
«Директор» есть кнопка «Назначить» / «Изменить»: вводите email и ФИО, приложение через
Supabase Auth Admin API отправляет директору письмо-приглашение и сразу создаёт для него
профиль (`role='director'`, привязка к филиалу). Это работает только если задан
`SUPABASE_SERVICE_ROLE_KEY` (см. выше) — без него кнопка вернёт ошибку с понятным текстом.

**Владельцев и CEO** тоже можно добавлять из приложения — карточка «Пользователи с полным
доступом» вверху `/dashboard` (видна владельцу и CEO). У роли `ceo` те же права, что у `owner`
(полный доступ ко всем филиалам, кварталам, назначениям), плюс два эксклюзивных поля:
«Комментарий/рекомендации от CEO» в аттестации и возможность добавлять пункты ИПР, помеченные
бейджем «CEO» (владелец их видит, но не может их редактировать — это ограничение только
интерфейсное, как и разграничение self/manager-оценок в аттестации, а не RLS: CEO и владелец
равны на уровне базы).

**Активность входов** — на `/dashboard/activity` (ссылка «Активность входов →» вверху
обзора, видна владельцу и CEO) — список всех входов в приложение: кто, когда, с каким email,
в какой роли и филиале. Каждый успешный вход на `/login` пишет строку в `login_events`;
журнал показывает только события с момента внедрения этой функции — более ранние входы в нём
не появятся.

**Сотрудники с доступом по блокам** — карточка «Сотрудники» на `/dashboard` (сразу после
«Пользователи с полным доступом», видна владельцу и CEO). В отличие от директора/владельца/CEO,
у роли `staff` нет фиксированного смысла — вы сами вводите ФИО, произвольную **должность** и
отмечаете, к каким **блокам компетенций** («Продажи», «ППО», «HR», «Маркетинг», «КЦ», «CQ»,
«FinDep») у человека есть доступ. Сотрудник видит `/dashboard` в урезанном виде (без управления
филиалами и пользователями, без «Активность входов») и на карточке любого филиала может
заполнять свою колонку «Оценка сотрудника» (см. ниже) только по тем компетенциям, у которых
блок компетенций совпадает с его доступом — самооценка директора, финальная «Оценка
руководителя» и текстовые поля (достижения, зоны роста, решение, комментарий CEO) ему
недоступны для правки. Это ограничение, как и разделение колонок между ролями, обеспечивается
интерфейсом, а не RLS: на уровне базы у staff есть чтение/запись всей строки аттестации сразу
по всем филиалам.

**Веса весовых блоков и компетенций теперь редактируются владельцем/CEO** — карточка «Блоки
итоговой оценки» на `/dashboard` (веса 4 блоков, раньше зашитые в коде как 35%/25%/20%/20%;
не обязаны суммироваться ровно в 100 — итог всегда считается как доля от суммы весов
заполненных блоков), и колонка «Вес в блоке» на карточке «Компетенции» (вес конкретной
компетенции относительно других в её весовом блоке — по умолчанию 1, все компетенции блока
равны; выше — сильнее влияет на среднее по блоку).

**Два независимых деления компетенций.** Каждая компетенция может иметь:
- **весовой блок** (1–4: «Бизнес-результат», «Управление командой», «Операционное
  управление», «Личная эффективность и лидерство», веса редактируемые) — по нему считается
  итоговый балл директора;
- **блок(и) компетенций** (7 департаментов: Продажи/ППО/HR/Маркетинг/КЦ/CQ/FinDep) — по ним
  определяется, какой сотрудник может заполнять «Оценку сотрудника» по этой компетенции и
  какой сотрудник может добавить новую компетенцию в этот блок. **Компетенция может относиться
  сразу к нескольким блокам одновременно** (например, «Клиентский сервис» — и к «Продажи», и
  к «КЦ») — доступ получает любой сотрудник, у которого есть доступ хотя бы к одному из них.

Эти два деления существуют параллельно и не обязаны совпадать. Управляются на карточке
«Компетенции» на `/dashboard` (видна владельцу и CEO): список всех компетенций с возможностью
поменять весовой блок, отметить чекбоксами один или несколько блоков компетенций, переименовать
или удалить, плюс форма добавления новой компетенции сразу со всеми блоками.

**Сотрудники сами добавляют компетенции.** У роли `staff` на `/dashboard` есть карточка
«Компетенции моего блока» — можно добавить новую компетенцию (название) в свой блок из списка
доступных. Такая компетенция сразу видна всем (владельцу, CEO, другим сотрудникам), но **не
попадает в лист аттестации и не считается в итоговом балле**, пока владелец или CEO не назначит
ей весовой блок на карточке «Компетенции» — до этого момента она значится «ожидает
подтверждения». Владелец/CEO может также поменять или удалить любую компетенцию, включая
добавленные сотрудниками.

**Важно после обновления:** до этой миграции `staff_block_access.block_id` хранил id весового
блока (`1`–`4`); теперь он хранит id блока компетенций (`sales`/`ppo`/`hr`/`marketing`/`kc`/
`cq`/`findep`). Если сотрудникам уже назначался доступ по старой схеме, переназначьте его в
карточке «Сотрудники» — старые значения `1`–`4` больше ничему не соответствуют.

**Порядок оценки.** Лист аттестации теперь показывает три колонки — «Самооценка» (директор),
«Оценка сотрудника» (staff, только по своим блокам компетенций) и «Оценка руководителя»
(владелец/CEO — финальная, единственная, которая закреплена как «Оценка руководителя» в
названии и участвует в итоговом балле напрямую). Пока владелец/CEO не проставили «Оценку
руководителя» по компетенции, итоговый балл временно берёт значение из «Оценки сотрудника», а
если и её нет — из самооценки; как только «Оценка руководителя» появляется, она замещает и то,
и другое. Рекомендованная последовательность — сотрудники по своим блокам → руководитель сети
(предпоследним) → CEO (последним) — показана текстовой подсказкой под итоговым баллом. Это
мягкая индикация, не блокировка: колонки можно заполнять в любом порядке, единственное жёсткое
правило — кто какую колонку вообще может редактировать (см. выше).

**Самооценка директора** отправляется один раз за квартал: пока не нажата кнопка «Отправить
самооценку», директор может свободно менять баллы и три поля «Ключевые достижения» (все три
обязательны). После отправки (`self_submitted = true`) поля блокируются для директора —
изменить их может только владелец/CEO кнопкой «Разблокировать» рядом с уведомлением. В таблице
филиалов на `/dashboard` рядом с именем директора — зелёная точка, если самооценка за активный
квартал отправлена, красная — если нет.

## 2. Запуск локально

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000). Неавторизованный пользователь
перенаправляется на `/login`. После входа `/` перенаправляет:

- владельца или CEO (`role = 'owner'` / `'ceo'`) → `/dashboard` (обзор всех филиалов)
- директора (`role = 'director'`) → `/branch/<его branch_id>` (карточка своего филиала)

Доступ разграничивается на уровне базы данных (RLS), а не в интерфейсе: даже если директор
откроет в адресной строке `/branch/<id-чужого-филиала>`, запросы к `attestations`/`ipr_items`
от его имени вернут пустой результат.

## 3. Структура проекта

```
app/
  login/page.tsx        — форма входа (email + пароль)
  dashboard/page.tsx     — обзор владельца (список филиалов, статистика, кварталы)
  branch/[id]/page.tsx   — карточка филиала: вкладки «Аттестация» / «ИПР»
  page.tsx               — редирект на основании роли из profiles
lib/
  supabase/client.ts      — Supabase-клиент для браузера
  supabase/server.ts      — Supabase-клиент для серверных компонентов
  supabase/proxy.ts       — обновление сессии + защита маршрутов (используется в proxy.ts)
  competencies.ts         — 4 весовых блока, 7 блоков компетенций, расчёт итогового балла
                            (сами компетенции — в таблице competencies, не здесь)
  types.ts                — типы таблиц базы данных
supabase/migrations/      — SQL для схемы и RLS (Фаза 1 и 2)
proxy.ts                  — Next.js 16 Proxy (бывший middleware): редирект на /login
```

> Next.js 16 переименовал `middleware.ts` → `proxy.ts` (см. `AGENTS.md`, автогенерируется
> `next dev` и указывает на версионную документацию в `node_modules/next/dist/docs/`).

## 4. Деплой на Vercel

1. Запушить код в GitHub-репозиторий.
2. В Vercel — Import Project → выбрать репозиторий.
3. Settings → Environment Variables — добавить `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` (без `NEXT_PUBLIC_` —
   должна остаться серверной).
4. Deploy.

## 5. Проверка разграничения доступа (Фаза 6)

1. Войдите под тестовым директором филиала А.
2. Убедитесь, что видно только филиал А (`/branch/<id-А>`).
3. Откройте в адресной строке `/branch/<id-Б>` — данные аттестации и ИПР филиала Б не
   загрузятся (RLS вернёт пустой набор строк), несмотря на то что страница технически
   рендерится.
